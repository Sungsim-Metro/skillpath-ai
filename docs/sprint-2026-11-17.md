## 작업 규칙

`CLAUDE.md`의 원칙이 먼저다. 이번 구현에만 적용하는 규칙은 아래와 같다.

1. **기능 하나에 브랜치 하나, PR 하나.** 브랜치는 항상 최신 `main`에서 딴다. 다른 기능 브랜치 위에 쌓지 않는다. 기능 하나를 빼도 나머지를 합칠 수 있어야 한다.
2. **0번을 먼저 합친다.** 화면 파일을 나눈 뒤에 나머지를 시작한다. 그래야 기능끼리 같은 파일에서 충돌하지 않는다.
3. **없어도 돌아가게 만든다.** 다른 기능이 합쳐지지 않았어도 동작해야 한다. 예: 레이더 차트는 수준 입력이 없으면 있다/없다로 그린다.
4. **인터페이스는 예전 형식도 받는다.** 형식을 넓힐 때 기존 호출이 깨지지 않게 한다. `contracts/`를 같은 PR에서 고치고 PR 설명 맨 위에 "인터페이스 변경"이라고 적는다.
5. **가짜 모드에서 끝까지 돈다.** `BEDROCK_MOCK=1`로 화면과 테스트가 돌아야 한다. 새 LLM 호출에는 `data/sample/`의 가짜 응답과 테스트를 함께 넣는다.
6. **세기는 코드.** 점수, 비율, 비용, 순위는 코드가 계산한다. LLM이 낸 숫자를 그대로 화면에 쓰지 않는다.
7. **PR 본문에 적는 것**: 무엇을 만들었나, 화면에서 확인하는 방법, 실제 Bedrock으로 확인했는지 여부, 검토자가 볼 곳, 이 기능을 빼려면 무엇을 하면 되는지.
8. **검토자는 자기 영역을 직접 고친다.** 댓글만 달지 않고 필요한 수정은 같은 브랜치에 커밋으로 얹는다. 발표 질의응답에서 그 부분을 설명할 수 있어야 한다.
9. **순서대로 만들고, 시간이 모자라면 뒤에서부터 뺀다.**

## 기능별 지침

"미정"은 그 기능을 시작할 때 형섭과 정하고 여기에 적는다. 정하지 않은 채로 만들지 않는다.

### 0. 화면 파일 나누기 (`refactor/app-tabs`)
- 할 일: `app/main.py`를 탭별 파일로 나눈다. 동작과 화면은 바꾸지 않는다.
- 완료 조건: 가짜 모드에서 나누기 전과 같은 화면이 나온다. 탭마다 파일이 하나다. 기존 테스트가 통과한다.
- 이 PR만 먼저 `main`에 합친다.

### 1. 보유 수준 3단계 입력 (`feat/skill-level`) — 인터페이스 변경
- 할 일: 기술마다 수준을 고르게 하고 Gap 계산과 추천 과정의 난이도 선택에 반영한다.
- 정해진 것:
  - 단계는 3개다. 수준을 고르지 않은 기술은 "없음"으로 본다.
  - `backend/api.py`의 `get_gap`, `get_area_gap`은 지금 형식(기술 이름 목록)도 그대로 받는다. 이름 목록으로 받으면 가장 높은 수준으로 본다.
  - 과정 난이도는 `data/courses/courses.csv`의 `level`을 쓴다.
- 미정: 단계의 이름과 화면 문구, 중간 단계를 Gap에서 얼마로 칠지, 수준과 과정 난이도를 짝짓는 규칙, 입력 화면 형태(영역별 묶음인지).
- 완료 조건: 수준을 바꾸면 Gap 수치와 추천 과정 난이도가 달라진다. `contracts/README.md`와 예시가 같은 PR에 있다. 예전 형식 호출 테스트가 통과한다.

### 2. 영역 레이더 차트 (`feat/radar-chart`)
- 할 일: 8개 영역에 대해 "공고 수요", "지금 내 보유", "추천 과정을 마친 뒤"를 한 차트에 겹쳐 그린다.
- 정해진 것:
  - 영역 값은 `get_area_gap`의 결과를 쓴다. "마친 뒤" 값은 추천 과정이 다루는 기술을 보유에 더해 코드로 다시 계산한다.
  - "마친 뒤"는 예상치다. 화면에 "추천 과정을 모두 마쳤을 때의 예상"이라고 적는다.
- 미정: 차트 라이브러리(지금은 altair만 쓴다. 레이더는 다른 라이브러리가 필요할 수 있다), 넣을 탭.
- 완료 조건: 보유를 바꾸면 차트가 바뀐다. 수요가 0인 영역이 있어도 깨지지 않는다. 계산 함수에 테스트가 있다.

### 3. 추천 카드의 신뢰 근거 (`feat/recommend-evidence`)
- 할 일: 추천 카드마다 "공고 n건 중 m건이 요구"와 "이 과정의 학습 목표 중 이 기술을 다루는 문장"을 보여준다.
- 정해진 것:
  - 일치 문장은 `data/courses/course_subskill.csv`의 `evidence`를 쓴다. 새로 만들어 내지 않는다.
  - 문장이 과정 원문(`courses.csv`의 `objectives`, `title`, `description`)에 실제로 있는지 코드로 검사한다. 없으면 보여주지 않고 "불확실"로 표시한다.
  - 공고 원문과 추출 근거 문장은 추천 화면에 보여주지 않는다(기존 원칙 유지).
- 미정: ③ 추천 형식에 필드를 더할지, 화면에서 조인할지.
- 완료 조건: 근거가 없는 추천은 "불확실"로 나온다. 검사 함수에 테스트가 있다.

### 4. 추천 에이전트 대 검증 에이전트 (`feat/recommend-debate`)
- 할 일: 추천 흐름을 두 역할로 나눈다.
  1. 추천 에이전트가 과정을 고르고 이유를 쓴다(지금의 `ai/recommend.py`).
  2. 검증 에이전트가 반박한다: 사용자 수준에 맞는가, 학습 목표가 부족 기술을 실제로 다루는가, 후보 중 더 맞는 과정이 있는가.
  3. 반박이 있으면 추천 에이전트가 한 번만 고친다. 두 번 이상 돌리지 않는다.
  4. 코드가 근거를 검사한다. 통과하지 못하면 "불확실"로 표시한다.
- 정해진 것:
  - 추출 단계에는 넣지 않는다.
  - 검증 에이전트는 후보 과정 목록 밖의 과정을 제안할 수 없다. 반박에는 과정 원문의 문장을 근거로 붙이고, 그 문장이 원문에 있는지 코드로 검사한다.
  - 끌 수 있어야 한다. 환경 변수 하나로 단일 추천과 토론 추천을 바꾼다. 평가에서 둘을 비교하기 위해서다.
  - 호출마다 `usage`를 남긴다. 결과는 캐시한다(시연 속도).
  - 화면에는 검증 결과를 한 줄로 보여준다(예: 검증 통과 / 수정됨 / 불확실).
- 미정: 구현 방식(코드에서 Converse를 두 번 부를지, Bedrock의 다른 기능을 쓸지), 상담 Agent(#25)가 이 흐름을 도구로 부르는 방식, 검증 에이전트의 모델.
- 주의: 두 에이전트가 같은 모델이면 같이 틀릴 수 있다. 효과는 5번의 채점으로 확인하고, 나아지지 않아도 결과를 그대로 적는다.
- 완료 조건: 가짜 모드에서 세 경우(통과, 수정, 불확실)가 테스트로 재현된다. 단일 추천과 토론 추천을 같은 입력으로 돌려 비교할 수 있다.

### 5. 평가 (`feat/eval-judge`)
- 할 일:
  - 추천 이유와 상담 답변을 채점 기준표에 따라 LLM이 채점하는 스크립트
  - 같은 항목을 사람이 채점하는 양식과, LLM 채점과 사람 채점의 일치율 계산
  - 실제 공고 정답셋을 늘리기 위한 초안 생성
- 정해진 것:
  - 개발 중에 돌리는 평가다. 서비스 실행 경로에는 넣지 않는다.
  - 점수의 합계, 평균, 일치율은 코드가 계산한다.
  - 정답셋 초안은 채점받을 프롬프트와 다른 버전으로 뽑는다. 같은 프롬프트로 뽑으면 점수가 부풀려진다.
  - **정답 확정과 사람 재채점은 사람이 한다(성진).** 초안을 그대로 정답으로 쓰지 않는다.
  - 프롬프트를 고칠 때 본 공고(`data/tuning_ids.json`)는 채점에서 뺀다.
- 미정: 채점 기준표의 항목과 척도, 정답셋 100개를 세는 단위(공고인지 기술 항목인지), 평가 질문 수, 사람 재채점 건수.
- 완료 조건: 명령 하나로 결과 표가 나온다(단일 추천 대 토론 추천 포함). 결과 파일에 실행일, 모델, 프롬프트 버전, 건수가 남는다.

### 6. 현직자 연결 카드 (`feat/mentor-connect`)
- 할 일: 부족 역량 결과 아래에 세 가지를 보여준다.
  1. 부족 영역에 맞는 AWS 한국 사용자 모임(AWSKRUG) 소모임
  2. 커피챗 요청 메시지 초안과 물어볼 질문 3개(내 Gap 결과 기준, LLM이 씀)
  3. 사람 찾기 검색 링크(LinkedIn 검색, 멘토링 서비스 검색). 사용자가 직접 누른다
- 정해진 것:
  - **사람 정보를 수집·저장·표시하지 않는다.** LinkedIn과 멘토링 서비스의 프로필을 자동으로 가져오지 않는다. 링크만 만든다.
  - 소모임 목록은 사람이 고른 데이터 파일(10개 안팎)로 둔다. 모임 이름, 주제, 링크, 대응 영역, 확인한 날짜를 적는다. 영역과 모임의 짝짓기는 코드가 한다.
  - 목록의 출처, 확인일, 한계를 `docs/data-sources.md`에 적는다.
  - 메시지 초안에는 사용자의 실제 정보를 지어내지 않는다. 이름 같은 자리는 빈칸으로 둔다.
- 미정: 목록에 넣을 모임(비수도권·온라인 참여 가능 여부 확인), 넣을 탭.
- 완료 조건: 부족 영역이 바뀌면 추천 모임이 바뀐다. 맞는 모임이 없으면 없다고 표시한다. 링크가 모두 열린다.

### 7. 폰 화면 폭 맞춤 (`feat/mobile-layout`)
- 할 일: 폰 화면 폭(약 390px)에서 모든 탭이 깨지지 않게 한다. 사용자 테스트 설문을 폰으로 받기 때문이다.
- 정해진 것: Streamlit을 그대로 쓴다. 화면 기술을 바꾸거나 앱을 만들지 않는다.
- 완료 조건: 폰 폭에서 가로 스크롤이 없고, 차트와 표가 읽히며, 보유 기술 입력이 가능하다. 탭별 폰 폭 화면 캡처를 PR에 붙인다.
- 1~6번의 화면이 들어온 뒤에 한다.

### 8. 토큰·비용 화면 (`feat/usage-dashboard`)
- 할 일: 호출 수, 입력·출력 토큰, 추정 비용을 단계별(추출, 추천, 검증, 상담)로 보여주는 화면 하나.
- 정해진 것:
  - 지금 남기고 있는 `usage`를 모아 쓴다. 비용은 코드가 계산한다. 토큰을 세는 에이전트는 만들지 않는다.
  - 단가는 설정 파일에 두고 출처와 확인일을 적는다. 화면에 "추정"이라고 적는다.
- 미정: `usage`를 어디에 모을지(파일, DynamoDB, CloudWatch), 화면 위치(탭인지 별도 페이지인지).
- 완료 조건: 호출 뒤에 숫자가 늘어난다. 가짜 모드의 호출은 실제 호출과 구분된다.

### 9. 과정 검색 방식 비교표 (`feat/search-compare`)
- 할 일: 키워드 기반, 임베딩 기반, 둘을 섞은 방식의 Top-5 적중률을 같은 질의로 비교하는 스크립트와 결과 표.
- 정해진 것:
  - 서비스가 쓰는 검색 방식은 이 PR에서 바꾸지 않는다. 결과를 보고 따로 정한다.
  - Reranking은 하지 않는다.
- 미정: 평가 질의와 정답 과정을 누가 정하는지, 임베딩 검색의 현재 상태(종훈 확인).
- 완료 조건: 명령 하나로 방식별 적중률 표가 나온다. 질의 수와 정답 기준이 결과에 적혀 있다.

### 10. 진단 보고서 내려받기 (`feat/report-download`)
- 할 일: 진단 결과 한 장(보유 수준, 영역별 Gap, 부족 기술, 추천 과정과 이유, 데이터 출처와 수집일)을 내려받는 버튼.

- 완료 조건: 내려받은 파일에서 한글이 깨지지 않는다. 폰에서도 열린다.
