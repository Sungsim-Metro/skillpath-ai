## 1. 결정 사항

### 방향
- 공고 → 추출 → Gap → 추천 흐름은 바꾸지 않는다. 11/16에 받은 조언은 그 위에 기능을 얹는 방식으로 반영한다.
- 기능을 늘리기보다 평가(정답셋, 채점, 비교표)에 시간을 쓴다.
- 대상 직무는 클라우드 엔지니어 하나로 한다. AI 직무는 하지 않는다(11/12 "두 직무 동시 진행"을 바꿈).

### 넣는 기능
| # | 기능 | 버는 점수 |
| --- | --- | --- |
| 1 | 보유 수준 3단계 입력. Gap과 추천 난이도에 반영한다 | 현장 적용성, 문제해결력 |
| 2 | 8개 영역 레이더 차트: 지금 / 추천 과정을 마친 뒤 | 전달력 |
| 3 | 추천 카드에 신뢰 근거: 공고 n건 중 m건이라는 수요 수치와 과정 학습 목표의 일치 문장 | 문제해결력 |
| 4 | 추천 단계의 멀티 에이전트: 추천 에이전트가 고르고, 검증 에이전트가 반박하고, 한 번만 고친 뒤 코드가 근거를 검사한다 | 창의성, AWS 활용도 |
| 5 | 평가: 추천 이유와 상담 답변을 LLM이 채점하고 일부를 사람이 다시 채점한다. 실제 공고 정답셋을 평가 케이스 100개 이상으로 늘린다 | 문제해결력 |
| 6 | 현직자 연결 카드: 부족 영역에 맞는 AWS 사용자 모임 소모임 추천, 커피챗 요청 메시지 초안과 질문 3개, 사람 찾기 검색 링크 | 현장 적용성, 창의성 |
| 7 | Streamlit 화면을 폰 화면 폭에 맞춘다 | 전달력 |
| 8 | 토큰·비용 화면: 호출 수, 토큰, 추정 비용. 계산은 코드로 한다 | AWS 활용도 |
| 9 | 과정 검색 방식 비교표: 키워드 / 임베딩 / 둘을 섞은 방식의 Top-5 적중률 | 문제해결력 |
| 10 | 진단 보고서 내려받기 | 현장 적용성, 전달력 |

### 코드 없이 하는 일
- 페르소나를 화면 첫 줄과 발표 첫 장에 적는다.
- 유사 서비스 비교표 한 장을 만든다(창의성).
- 시장 Gap(수요 − 공급) 차트를 교육과정 설계자용 리포트로 설명한다.

### 하지 않는 것
- 화면을 React나 앱으로 다시 만들기, 트렌드 분석 기능, 대화 기록 기반 공고 추천, Reranking, 임베딩 차원·청크 길이 변경
- Supervisor 구성. 멀티 에이전트는 위 4번(추천 대 검증)으로 한다.
- LinkedIn에서 사람을 직접 조회하기. 공식 API로는 사람 검색을 할 수 없고 자동 수집은 LinkedIn 약관이 금지한다. 사용자가 직접 누르는 검색 링크만 준다.
- 추출 단계에는 토론을 넣지 않는다. 호출이 공고 수만큼 늘고, 근거 문장은 이미 코드가 검사한다.

### 진행 방식
- 구현은 형섭이 Claude Code로 먼저 한다. 시간이 촉박해 분업하지 않는다.
- 기능마다 `main`에서 브랜치를 따고 PR을 올린다. 팀원은 PR별로 검토를 맡는다. 뺄 기능은 PR을 닫는다.
- 팀원의 기존 작업(공고 30건, 상담 Agent, Guardrails, E2E)은 그대로 각자 한다.
- 구현 지침은 `docs/sprint-2026-11-17.md`에 모은다(별도 PR).
- 사용자 테스트용 접속 주소는 형섭이 가진 도메인의 하위 주소로 한다.

## 3. 기준선 대비 점검
- 범위에 추가된 것: 위 기능 1~10, 사용자 테스트 규모(3~5명 관찰 → 약 30명 설문), 배포
- 범위에서 뺀 것: AI 직무
- 지연된 마일스톤: M3(11/17). 공고 30건 적재(#19)와 추출 정확도 측정(#21)이 열려 있다. 보드 확인 필요
- 인터페이스 변경(예정): 보유 수준 입력으로 화면 → backend의 보유 기술 형식이 "기술 이름 목록"에서 "기술과 수준"으로 바뀐다. 예전 형식도 받게 만든다. 추천에 난이도를 맞추면 ③ 추천의 선택 기준이 바뀐다
- 기존 결정과 달라지는 것(확정되면 `CLAUDE.md`와 `docs/planning.md`를 고친다):
  - "모바일 대응 안 함" → 폰 화면 폭 맞춤은 한다. 앱은 만들지 않는다
  - 11/12 "현직자 커피챗·멘토 추천은 만들지 않는다" → 사람을 조회하지 않는 현직자 연결 카드는 만든다
  - 11/12 "추출 검증에 AI를 한 번 더 부르지 않는다" → 그대로 지킨다. 추천 단계의 검증 에이전트와 개발 중 평가(LLM 채점)는 이 결정의 대상이 아니다
  - 11/10 "Agent는 최소형(단일, 도구 2개)" → 상담 Agent는 그대로 두고 추천 흐름에 에이전트 둘을 더한다
  - 11/13 "정답셋 20건" → 평가 케이스 100개 이상
- 위험:
  - **분량.** 기능 10개가 한 사람 기준 약 8~9일분(추정)인데 2.5일에 한다. 순서대로 만들고 모자라면 뒤에서부터 뺀다
  - **팀워크 기록.** PR 작성자가 모두 형섭이 된다. 검토자가 자기 영역은 직접 고쳐 커밋을 얹고, 발표 질의응답에서 설명할 수 있어야 한다
  - **배포.** 30명이 각자 접속하려면 11/19까지 접속 주소가 필요하다. 지금은 로컬 실행뿐이다
  - **토론의 효과.** 두 에이전트가 같은 모델이라 같이 틀릴 수 있다. 단일 추천과 같은 채점표로 비교하고, 나아지지 않아도 결과를 그대로 적는다
  - **사람이 할 일.** 정답셋 확정과 재채점은 사람이 해야 수치로 쓸 수 있다
