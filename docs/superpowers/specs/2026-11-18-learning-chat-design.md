# 학습 상담 채팅 설계 초안

2026-11-18 · 설계 검토용

사용자는 경험을 여러 메시지에 나눠 말하고, 현재 상태를 확인한 뒤, 원할 때 부족 역량이나 교육과정을 물어볼 수 있다. 메시지 전송은 발화 하나를 제출하는 동작이다. 분석·추천·저장은 각각 사용자가 요청한 범위에서 실행한다.

## 대화 한 번에 어디까지 실행하는가

| 사용자가 보낸 말 | 채팅의 응답 | 실행할 후속 작업 |
| --- | --- | --- |
| “프로젝트에서 제가 Docker로 API를 배포했어요.” | 직접 한 일을 이번 상담에 반영하고 짧게 확인한다. | 없음 |
| “그리고 배포할 때는 제가…” | 이어서 입력할 수 있게 기다린다. 미완성 부분은 역량으로 등록하지 않는다. | 없음 |
| “지금까지 말한 내 경험을 정리해줘.” | 이번 상담의 목표 직무·보유 기술·직접 맡은 일을 보여준다. | 없음 |
| “클라우드 엔지니어 기준으로 뭐가 부족해?” | 공고 수요와 현재 보유 기술을 비교한 결과를 돌려준다. | 수요 조회와 부족 역량 계산 |
| “그중 먼저 들을 교육과정을 추천해줘.” | 부족 역량과 연결된 과정, 추천 이유, 불확실 여부를 전달한다. | 현재 조건에 맞는 부족 역량 결과 확보 → 과정 추천 → 검증 |
| “방금 말한 Docker 배포 경험을 프로필에 저장해줘.” | 지정한 항목과 실제 저장 결과를 알려준다. | 요청한 항목만 프로필에 반영 |
| “AI 엔지니어로 취업하려면 뭘 준비할까?” | 현재 지원하는 직무를 안내하고 이 요청을 마친다. | 없음 |

“무엇부터 공부할까?”에는 수요에 따른 기술 우선순위까지 답할 수 있다. “어떤 강의를 들을까?”처럼 과정을 찾는 의도가 분명할 때 과정 검색을 시작한다. “추천은 나중에”, “아직 입력 중”처럼 보류 의사가 있으면 해당 작업을 실행하지 않는다. “내 상태 좀 봐줘”처럼 요약과 비교 중 어느 쪽인지 모호하면 현재 상태를 먼저 보여주고 원하는 비교 기준이 있는지 짧게 묻는다.

## 채팅이 정리하는 정보

- **목표 직무**는 이번 요청에서 상담받으려는 직무다. 현재 공통 지원 목록에는 클라우드 엔지니어가 있다. 과거 직무나 프로젝트에서 언급한 분야는 목표로 해석하지 않는다. 채팅에 명시한 목표가 미지원이면 사이드바에 선택된 직무로 대체하지 않는다. “AI 인프라”처럼 두 해석이 가능하면 클라우드 엔지니어 관점의 상담을 원하는지 한 번 묻는다. 향후 AI 직무의 데이터와 추천이 준비되면 공통 목록을 확장하고 안내 문구도 그 목록에서 생성한다. [지원 직무 목록](../../../backend/jobs.py)
- **보유 기술과 프로젝트 경험**은 사용자가 선택하거나 직접 했다고 진술한 내용에서 가져온다. “Docker를 배우고 싶다”는 상담 상태와 후속 입력에서 제외한다. “팀이 Kubernetes를 썼고 나는 API를 개발했다”에서는 API 개발만 본인의 경험으로 반영한다. 숙련도나 사용 기술을 프로젝트 이름에서 추정하지 않는다.
- **이번 상담 상태**는 저장된 프로필, 사용자가 실제로 선택한 사이드바 값, 현재 대화에서 추가·정정한 사실을 합쳐 구성한다. “Docker는 제가 쓴 게 아니에요” 같은 정정은 이번 상담의 기존 사실에도 적용한다. 화면의 초기 예시 선택값은 사용자 진술로 취급하지 않는다. 현재 화면은 수요 목록에 있는 Python·Linux·Git을 기본 선택하므로, 채팅에 전달할 때 사용자 입력 여부를 구분해야 한다. [사이드바](../../../app/main.py) · [기본 선택값](../../../app/common.py)
- **프로필 쓰기**는 분석 요청과 별개다. “기억해줘”, “프로필에 반영해줘”처럼 저장 의사가 분명할 때 대상 항목만 쓴다. 대상이 모호할 때만 확인한다. 대화에서 정정한 사실은 별도의 저장 요청이 있을 때까지 이번 상담에서만 적용한다. 저장 연결이 없거나 쓰기에 실패하면 그 사실을 알리고 세션의 정리 내용은 유지한다.

## 에이전트와 백엔드의 경계

1. **입구에서 요청을 점검한다.** 원래 메시지에 서비스 가드레일을 적용한다. 차단된 요청은 상담 상태를 변경하거나 후속 도구를 호출하지 않는다. 안전 정책을 통과한 요청도 목표 직무의 지원 여부를 별도로 확인한다. 다른 분야의 단어가 등장했다는 사실만으로 차단하지 않는다.
2. **채팅 에이전트가 상태와 요청을 정리한다.** 이번에 추가·정정할 사실, 목표 직무, 원하는 답변 범위(요약·부족 역량·과정 추천), 명시적 저장 요청을 구분해 백엔드에 넘긴다. 예를 들어 “이 경험을 저장하고 뭐가 부족한지 봐줘”에는 저장과 부족 역량 비교가 함께 들어간다. 후속 에이전트에는 맡은 작업에 필요한 값만 전달한다.
3. **백엔드가 호출 범위를 결정한다.** 요약은 세션 상태로 답한다. 비교에는 목표 직무와 표준 보유 기술 목록을 기존 `get_gap`에 전달한다. 과정 요청에는 현재 직무·보유 기술·수요 기준에 맞는 부족 역량 결과를 쓰고, 부족 기술이 있을 때만 `get_recommendations`로 이어간다. 현재 함수는 보유 기술 이름을 받으므로 프로젝트 경험은 사용자가 직접 썼다고 밝힌 기술을 통해 계산에 반영한다. 부족 역량은 사용자가 밝힌 정보와 공고의 차이라는 뜻이다. [백엔드 함수](../../../backend/api.py)
4. **추천과 검증은 후속 단계가 맡는다.** 기존 추천 경로는 과정 후보와 수요 수치를 바탕으로 추천 이유를 쓰고 코드가 과정 ID와 숫자 등을 검사한다. 팀이 설계한 추천·검증 에이전트를 연결하면 추천안을 검토하고 필요할 때 한 번 수정한 뒤 코드로 근거를 확인한다. 채팅은 이 결과를 받아 설명한다. [기존 검증](../../../ai/recommend.py) · [추천·검증 에이전트 결정](../../meetings/2026-11-16.md)
5. **답변은 확인된 결과를 따른다.** 수요 건수, 과정명, 링크와 매칭 상태는 반환값을 사용한다. 수요 데이터가 없으면 비교할 수 없다고 알린다. 검증을 통과한 과정이 없으면 확인 가능한 부족 역량까지만 답하고, 추천 결과가 비었거나 검증에 실패했다는 사유를 구분해 알려준다. [추천 반환 형식](../../../contracts/README.md)

## 실행 방식과 비용

경험을 입력할 때마다 전체 분석을 실행하면 첫 답에 과정까지 보여줄 수 있지만, 사용자가 뒤이어 내용을 정정하면 추천을 다시 만들게 된다. 이번 설계에서는 합의한 대로 메시지에서 요청한 단계까지만 실행한다. 사용자는 별도 모드 전환 없이 “그럼 과정도 추천해줘”라고 이어갈 수 있다.

**화면 연결 제안.** 현재 대시보드는 실행할 때 모든 탭의 `render`를 순회한다. 부족 기술이 있으면 추천 탭은 `get_recommendations`를 즉시 호출한다. 채팅을 같은 루프에 탭 하나로 추가하면 상태를 정리하는 메시지만 보내도 캐시가 비어 있을 때 추천 모델이 호출될 수 있다. 채팅을 같은 앱의 별도 화면으로 두고, 채팅 화면에서는 사이드바의 사용자 입력을 공유하되 대시보드 탭 렌더링을 건너뛴다. 이미 보여준 답변은 세션에서 다시 그리고, 화면 재실행만으로 같은 메시지의 도구 호출이나 저장을 반복하지 않는다. [화면 진입점](../../../app/main.py) · [추천 탭의 호출 지점](../../../app/tabs/recommend.py)

**비용 기준.** 정보 입력·상태 요약·부족 역량 비교에서 과정 검색, 추천 생성, 추천 검증 호출은 각각 0회여야 한다. 이 기준은 입력 가드레일이나 대화 이해에 드는 비용과 구분한다. 검증할 때는 실제 AWS 호출 없이 모의 함수로 호출 횟수를 확인한다.

## 구현 후 확인할 대화

| 시나리오 | 통과 조건 |
| --- | --- |
| 추천 캐시가 비어 있고 부족 기술이 있는 사용자가 경험을 세 번에 나눠 보낸다. 이어서 “내 상태만 정리해줘”라고 한다. | 세션에 본인의 경험만 모인다. 네 번의 전송 전체에서 후속 분석·추천·저장이 0회다. |
| 같은 대화에서 “뭐가 부족해?” 다음에 “그럼 어떤 과정을 들을까?”라고 한다. | 첫 답은 부족 역량에서 끝난다. 두 번째 요청에서만 부족 기술에 대한 과정 추천·검증이 실행된다. |
| 학습 희망과 팀원의 작업을 함께 언급하거나 이전 진술을 정정한다. | 희망·팀원의 기술이 보유 기술이나 추천 조건에 들어가지 않는다. 다음 비교는 정정된 상태를 사용한다. |
| 사이드바는 클라우드이고, 채팅에서는 AI 엔지니어가 목표라고 한다. 다음에는 클라우드 직무를 준비하며 AI 모델을 배포한 경험을 설명한다. | 첫 요청에는 지원 범위만 안내하고, 두 번째 요청에서는 본인이 한 클라우드 관련 경험을 반영한다. |
| 상태 정리 후 Docker 경험만 저장해 달라고 한다. 화면을 다시 실행한다. | 해당 경험만 한 번 저장한다. 저장 전 대화·재실행만으로 프로필 쓰기가 발생하지 않는다. |
