# 역량 분류 체계 (제안)

작성일 2026-11-12. 11/12 회의 확정 대기. 근거 파일: 형섭이 NCS에서 내려받은 직무기술서 엑셀(인공지능·클라우드 13개 직무, 2026-11-12 기준). 원본 파일은 재배포 조건을 확인하기 전까지 저장소에 올리지 않는다.
관련 이슈: #13(별칭 사전), #17(Gap 화면), #20(NCS 능력단위 매핑).
집계는 전부 코드로 셌다. 분류 배정(어느 능력단위를 어느 영역에 넣는가)은 사람이 판단한 것이므로 종훈·성진 검토가 필요하다.

## 1. NCS 파일에서 확인한 사실
- 13개 직무, 능력단위 114개, 능력단위요소 405개, 지식 1,645항목, 기술 1,560항목
- 클라우드 직무 5개(37개 단위), 인공지능 직무 7개(68개 단위), AIoT 1개(9개 단위)
- NCS 문장에는 도구 이름이 거의 없다. 지식·기술 3,205항목 중 쿠버네티스 1건, 쉘 스크립트 2건, RAG 1건. Docker, Terraform, IaC, Python, Jenkins, Ansible, AWS는 0건
- 반대로 절차 용어가 많다. 테스트 162건, 요구사항 140건, 품질 127건
- 영역별 분량이 고르지 않다. 보안은 12개 단위, 배포 자동화는 2개, 비용은 1개
- 직무숙련기간이 1년부터 시작하는 단위는 24개뿐이다. 나머지 90개는 2년 이상

결론: NCS 직무 구분을 그대로 범주로 쓰면 안 된다. 직무 구분은 "계획 → 설계 → 구현 → 테스트" 같은 업무 절차 순서라서 AWS 과정과 맞지 않고, 공고에 나오는 도구 이름도 담지 못한다.

## 6. 구현에 미치는 영향
- **인터페이스 JSON 변경**: ② 추출 결과와 ④ 수요 집계의 기술 항목에 `area_id`, `subskill_id` 두 필드가 생긴다. 가장 단순한 방법은 JSON은 그대로 두고 별칭 사전(표준 기술명 → 영역, 세부 능력, NCS 코드)을 따로 두어 집계·화면에서 조인하는 것이다
- 영역·세부 능력 배정은 LLM이 아니라 사전 조회(코드)로 한다. 사전에 없는 기술은 "미분류"로 두고 사람이 넣는다
- 화면: 영역 8개 레이더(내 보유 vs 공고 수요) + 세부 능력 막대. 5주차 기준 "Gap 차트 2개 이상"을 채운다
- 공고 30건으로 세부 능력 31개를 나누면 칸마다 표본이 얇다. 통계는 영역 단위로 보여주고, 세부 능력에는 공고 건수를 같이 적는다. 3건 미만이면 "표본 부족"으로 표시한다
- AWS 과정 20~30개는 영역마다 2~4개씩 고른다. 과정이 없는 세부 능력은 비워 두고 "대응 과정 없음"으로 표시한다

## 7. 회의에서 정할 것
1. 8개 영역 이름과 개수 확정
2. JSON에 필드를 넣을지, 별칭 사전 조인으로 갈지 (일현·종훈)
3. 세부 능력별 과정 수집 담당과 기한 (종훈)
4. 멘토 질문: NCS 직무 구분 대신 AWS 도메인 기준으로 재구성해도 5주차 "NCS 역량 매칭" 기준을 충족하는가
