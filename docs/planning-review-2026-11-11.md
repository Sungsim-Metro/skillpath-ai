## 0. 결론

방향은 과제와 맞다. 계약 우선, 근거 문장 검증, "세기는 코드·이해는 AI", 가짜 데이터 모드, "공고 1건 → 추천 1건을 먼저"라는 마일스톤 구조는 과제 PDF와 4주차 수업이 요구한 것과 같다.

문제는 세 가지다.

1. **11/10 회의 결정 5개가 과제 문서·수업과 반대 방향이다.** S3 원본 저장 제외, 공고 직접 분석 탭 보류, NCS 화면 표시를 부가 기능으로, 학습 순서 보류, 직무 2개 확대와 사용자 입력 저장. (1절)
2. **수업이 정한 수치 기준과 "AWS 과제 기준"이 계획에 없다.** 4주차 교안 5쪽에 "AWS 과제 기준: 기술 완성도 30 · 분석 품질 25 · 추천 성능 20"이 있고, 추천 성능을 재는 방법이 우리 계획에 없다. (2절)
3. **실제 데이터가 0건이고 외부 의존이 세 개다.** 공고 API 키, 팀 계정의 Knowledge Base·Agent 권한, 동작하지 않는 Claude 리뷰. (4절)

필수를 3개 올리고(공고 직접 분석 탭, 학습 순서 최소형, NCS 최소형) 4개를 내리면(API Gateway, DynamoDB 사용자 저장, AI 엔지니어 직무는 M3 뒤 데이터 추가, React 전환) 일은 줄고 과제 적합도는 올라간다.

### 어긋난 점과 제안

**A. 공고 직접 분석 탭을 필수로 되돌린다.** *회의 결정과 다름*
- 과제의 끝까지 연결은 "채용공고 한 건이 들어와 추천 한 건이 나오는" 흐름이다. 우리 정의(보유 기술 → Gap → 추천)는 5단계 중 4·5단계만 실시간으로 보여준다. 녹취: "좋은 모델을 사용해도 마지막 추천까지 연결되지 않으면 결과가 아쉽다."
- 이 탭은 PR #33으로 이미 화면이 있다. M2(실제 공고 1건 → 추천 1건)의 추출 함수를 그대로 부르면 된다. 추가 작업은 추출 결과 아래에 "이 공고 기준 내 부족 기술과 추천"을 한 번 더 부르는 것뿐이다.
- 발표의 핵심 장면 후보다(3절 전달력).

**B. S3 `raw/` → Lambda → Bedrock → S3 `processed/`를 그대로 쓴다.** *회의 결정과 다름*
- PDF 1단계 카드 아래에 "S3 · Lambda"가 적혀 있고, 4주차 실습 3이 이 구조다. 실습에서 받은 `infra/week4-pipeline.yaml`(CloudFormation)을 재사용하면 새로 설계할 것이 없다.
- 근거 문장 검증(#16), 프롬프트 재실행, 정확도 측정(#21)에 같은 원문이 필요하다. 마감된 공고는 다시 받을 수 없다.
- API Gateway는 과제 PDF·녹취·4주차 교안 어디에도 없다. Lambda는 S3 이벤트로 돌리고 화면은 함수(boto3)를 직접 부른다. #18의 "엔드포인트 3개"는 "화면이 부르는 함수 3개"로 충분하다.

**C. NCS 연결을 최소형으로 필수에 넣는다.** *회의 결정과 다름*
- PDF 4단계 이름이 "분석 · NCS 연결"이다. 4주차 교안은 Skills Gap을 "산업 수요 vs NCS 표준 비교"로, 5주차를 "채용공고 역량 ↔ NCS 역량 매칭"으로 예고했다. 강사 소개에도 "이번 과제의 NCS 역량과 직접 연결"이 있다.
- 최소형: 수요 상위 10개 기술에 NCS 능력단위 이름을 붙여 탭 1에 표시한다(② 형식의 `ncs_unit`은 이미 있다). 대응하는 능력단위가 없는 기술은 "NCS에 없는 신규 기술 후보"로 따로 센다. 이것이 과제가 말한 "산업 수요와 표준의 차이"이고, 4주차 팀 과제("사전에 없는 신규 기술 후보 정리")와도 이어진다.
- 수업에서 신청한 공공데이터포털 NCS API 키가 있으면 그것으로 받는다. 커리큘럼 첫 항목인 "공공 API 데이터 수집"의 근거가 된다. 지금 주 수집 경로에는 공공 API가 없다.

**D. 학습 순서를 최소형으로 필수에 넣는다.** *회의 결정과 다름*
- PDF 3쪽: "입력이 있으면 학습 순서를 제안할 수 있습니다." 녹취의 한 문장 정의도 "다음에 무엇을 공부할지"이고, 에이전트 예시 질문도 "무엇부터 공부해야 되나요?"다.
- 최소형: 추천 목록을 코드로 정렬한다. 선수지식이 없는 기초 과정 먼저, 같은 단계에서는 수요가 높은 기술 먼저. 화면에는 번호와 "왜 이 순서인지" 한 줄. LLM을 쓰지 않는다.

**E. 직무는 클라우드 엔지니어 하나를 30건 이상으로 끝까지 간다.**
- 직무가 둘이면 정답지, 별칭 사전, 교육과정 표가 두 벌이다. 공고 40건을 둘로 나누면 "20건 중 n건"이 되어 통계가 약해진다.
- AI 엔지니어는 M3 통과 뒤 같은 파이프라인에 데이터만 추가한다. M4까지 30건이 안 되면 뺀다. "30건 이상"은 직무별 기준으로 적는다.
- `CLAUDE.md`의 "하지 않는 것: 다중 직무"와 #19의 "직무 1개 기준"이 회의 결정과 어긋난 채 남아 있다. 회의에서 확정한 뒤 한 번에 고친다.

**F. 사용자 입력은 저장하지 않는다.** *회의 결정과 다름*
- 과제 문서 어디에도 사용자 정보 저장 요구가 없다. 6주차 항목이 "공정성·개인정보 점검"인데, 저장하면 점검 대상이 늘고 점수 근거는 없다.
- 추출 결과는 S3 `processed/` JSON으로 충분하다(30~50건). DynamoDB는 "왜 S3가 아니라 DynamoDB인가"에 답할 수 있을 때만 쓴다. 쓴다면 기술별 집계 조회용 표 하나로 한다.

### 표준화 주의 (#13)
- 임베딩만으로 합치면 Java와 JavaScript가 붙는다. 4주차 교안의 순서를 따른다: LLM으로 넓게 뽑고 → 사전으로 대표명에 맞추고 → 사전에 없으면 신규 후보로 모은다. 임베딩 유사도는 후보를 찾는 데만 쓰고 기준 미달은 `uncertain`.
- `backend/api.py` 가짜 모드의 부분 문자열 매칭과 `EKS → Kubernetes`, `IaC → Terraform` 같은 별칭은 실제 사전으로 옮기지 않는다. 과하게 합치는 예다.
- 형태소 분석으로 기술명을 자르지 않는다(교안: `k8s → ['k', 's']`).

### 페르소나와 데이터가 어긋난다
- 페르소나는 신입 지원자인데 수집 대상은 대부분 경력 공고다(우리 근거 통계: 공고의 82%가 경력만).
- 제안: 공고에 경력 구분(신입·경력 무관·경력)을 남기고 탭 1에 "신입 지원 가능 n건 / 전체 m건"을 보여준다. 한계로만 적는 것보다 화면에서 구분해 주는 쪽이 현장 적용성 질문("신입에게 이게 맞는 기준인가")에 답이 된다. → 5절 인터페이스 변경 제안

### AWS 과제 기준 (4주차 교안 5쪽)

"대회 평가: 문제해결력 · 현장 적용성 · 창의성 · 전달력 · AWS 과제 기준: **기술 완성도 30 · 분석 품질 25 · 추천 성능 20**"

- 합이 75다. 나머지 배점과, 이 기준이 OT의 "AWS 기술 활용도 및 팀워크 20"과 어떤 관계인지는 **LMS·멘토 확인 필요**. 11/12 멘토링 첫 질문으로 올린다.
- 녹취의 "서비스가 실제로 연결돼서 잘 작동하는지, 분석이 타당한지, 추천이 적절한지"와 순서까지 같다. 배점이 어떻게 쓰이든 AWS 심사위원이 보는 세 가지로 읽는다.

| AWS 기준 | 우리가 내놓을 증거 | 지금 상태 |
| --- | --- | --- |
| 기술 완성도 30 | 공고 1건 → 추천까지 자동 테스트 통과, S3 → Lambda 자동 처리 로그, Agent 도구 호출 | E2E 이슈 없었음, Lambda 쓰임새 미정 |

### 창의성: 싸게 얻는 차별점 3개
1. **내가 지원할 그 공고로 진단한다.** 시장 평균이 아니라 붙여 넣은 공고 1건 기준의 부족 기술과 추천(공고 직접 분석 탭 확장).
2. **검증 통과율을 화면에 공개한다.** "추출 n개 중 근거 검증 통과 m개, 불확실 k개." 검증 코드(#16)의 부산물이라 추가 작업이 거의 없다. "검증 가능한 흐름"이라는 과제 핵심을 숫자로 보여준다.
3. **NCS에 없는 신규 기술 후보.** 표준과 시장의 차이를 한 줄 목록으로(1절 C).

### 공정성·개인정보: 지금 결정의 문제
- Guardrails가 "지역"을 막는데 페르소나의 핵심이 "비수도권"이다. "지방에서 준비하려면?" 같은 정상 질문이 막힌다. "학력"도 "비전공자인데"가 걸릴 수 있다.
- 제안: 단어가 아니라 행위로 나눈다.
  1. 추출: 나이·성별·학력·지역 같은 인적 조건은 기술로 뽑지 않는다(프롬프트 규칙 + 코드 필터).
  2. 추천: 입력은 보유 기술뿐이다. 인적 속성을 받지 않으므로 추천이 그에 따라 달라질 수 없다. 이것이 가장 강한 공정성 근거다.
  3. Guardrails: 주제 외 질문과 "특정 성별·연령에 맞는 직무를 골라 달라" 같은 차별적 추천 요청을 거절한다.
  4. 개인정보: 공고 원문의 담당자 이름·전화번호·이메일은 저장 전에 가린다. 사용자 입력은 저장하지 않는다.
  5. 수집 편향: 출처 플랫폼의 기업 유형 편중, 경력 공고 편중, 수집 기간을 `docs/data-sources.md` 한계 칸에 적는다.

### 팀워크: 리뷰가 실제로는 0건이다
- 11/10 결정은 "Claude 리뷰만 받고 올린 사람이 병합"인데, Claude Review 워크플로는 PR #35에서 두 번 실패했고 #31의 `@claude` 호출도 에러로 끝났다. 지금은 아무 리뷰 없이 병합되는 상태다.
- 제안: 워크플로를 고치는 것과 별개로, 계약으로 이어진 옆 구간 담당자가 PR에 "형식 확인" 한 줄을 남긴다(종훈 ↔ 성진, 성진 ↔ 일현, 일현 ↔ 형섭). 5분이면 되고, 심사 문구 "역할 분담과 협업"의 직접 증거다. 질문 유형 "이 부분은 누가 만들었나요?"에는 이슈 담당자가 각자 답한다.
