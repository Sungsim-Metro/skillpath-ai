# 발표 초안

2026-11-21 작성. 11/25 발표(15분 + 질의응답 7분)의 초안입니다. 시간 배분은 아직 넣지 않았고, **과제 요구사항을 충족했는지**와 **평가 항목별로 점수를 받을 포인트**를 먼저 정리했습니다.
시연 순서는 [시연 시나리오](demo-scenario.md)에 있습니다. 평가 기준과 과제 요구는 [과제 내용](assignment.md)을 따릅니다.

숫자는 저장소 문서에 있는 값만 썼고 출처를 옆에 적었습니다. 값이 없는 곳은 지어내지 않고 **[채울 칸]** 으로 두었습니다(7절).

## 1. 요구사항 충족 진단

| --- | --- | --- | --- |
| 1 데이터 수집 | 충족 | 클라우드 엔지니어 230건(로켓펀치 18 + 원티드 212), AI 엔지니어 687건(71 + 616). 수집한 공고 JSON은 S3에 둠. 출처·범위·한계를 [데이터 출처](data-sources.md)에 기록 | 직무 판정은 모델이 했고 사람이 전수 검토하지 않음 |

| 확신 없으면 "불확실" | 강하게 충족 | 불확실 기술은 수요 집계에서 제외, 기준 단계 옆 "(불확실)", 추천 카드의 "유사 과정", 관리자 화면의 과정 커버리지 | |

요약: 흐름 5단계는 끝까지 이어져 있고 "근거"와 "불확실"은 과제가 요구한 것보다 엄격하게 지켰습니다. 약한 곳은 **정확도를 증명할 채점 수치**, **AI 직무의 기술 사전**, **Lambda** 세 가지입니다.

## 2. 평가 항목별 득점 포인트

### 문제해결력 (20)

심사 질문: 핵심 문제를 이해하고 논리적으로 접근했나.

- 과제의 5단계를 그대로 따라가고, 세 질문에 장표 하나씩으로 직접 답합니다.
- **측정하고 고친 기록**을 붙입니다. 개선 기록(`ai/eval/IMPROVEMENT_LOG.md`)에 문제를 무엇으로 알았는지, 무엇을 바꿨는지, 숫자가 어떻게 바뀌었는지가 있습니다.
  - 불확실 비율 56.2% → 11.6% (실제 공고 12건, 1회)
  - 표기가 애매한 질문의 응답 46.2초 → 9.8초
  - 추천 화면의 모델 호출 6번 → 3번, 다시 그리면 0번
- "세기는 코드, 이해는 AI"라는 역할 구분이 논리의 뼈대입니다. 빈도, 비율, Gap은 코드가 계산합니다.

### 현장 적용성 (20)

심사 질문: 실제 현장 문제 개선에 도움이 되는 시도인가.

- 페르소나: 클라우드 경험이 없는 컴퓨터공학 4학년이 실제 공고가 요구한 기술과 자기 기술을 비교해 무엇부터 공부할지 확인합니다(`docs/planning.md`).
- 실제 사용 흐름: 경험을 말하면 관련 수준 문항을 묻고, 부족 역량과 교육과정으로 이어집니다. 비회원도 전부 볼 수 있습니다.
- 사용자 테스트 결과 **[채울 칸]**.
- 데이터 이용 조건을 확인하고 지킨 과정: AWS 교육과정은 대회 측에 물어 답을 받았고, 원티드는 약관 확인 뒤 페이지 조회를 중단했습니다.
- 교육과정을 만드는 쪽에도 쓸모가 있습니다(3절 1번).

### 창의성 (20)

심사 질문: 데이터·시간 제약 안에서 창의적인 아이디어인가.

이전에 내세운 차별점(검증 통과율 공개, 영역별 Gap, 신규 기술 후보)은 외부 검토에서 두 번 약하다는 평가를 받았습니다. 3절의 1~3번을 앞세웁니다.

- 수요는 있는데 AWS 과정이 없는 기술을 찾아내는 지표
- LLM의 답을 코드와 별도 호출로 검증한 뒤에만 보여 주는 구조
- 모델과 추천 구조를 실험으로 비교하고 코드 규칙으로 고르는 운영

"제약 안에서"라는 말에 맞춰, 로켓펀치 조회 한도 때문에 공고가 18건뿐이던 상황을 오픈 데이터셋으로 푼 과정도 한 줄 넣습니다.

### 전달력 (20)

심사 질문: 아이디어와 결과물이 명확하고 이해하기 쉬운가.

- 라이브 시연이 세 질문에 화면으로 답하게 짭니다. 시연 단계마다 "지금 보신 것이 질문 몇 번의 답"이라고 말합니다.
- 장표마다 숫자 하나와 한 문장만 둡니다.
- 첫 장은 페르소나, 마지막 장은 소개 페이지 주소와 QR입니다.

### AWS 기술 활용도 및 팀워크 (20)

심사 질문: AWS 서비스를 적절히 선정하고 역할 분담·협업이 잘 됐나.

- 서비스마다 "왜 이것인가"를 한 줄씩 답합니다(5절 장표 9). **코드에서 확인되는 것만** 그립니다.
- "테스트"가 아니라 운영 관점으로 설명합니다: 호출마다 토큰 기록, 관리자 화면의 비용 집계, 캐시로 줄인 호출 수. 월 운영비 추정 **[채울 칸]**.
- 팀워크: 구간 담당 4명, `contracts/`의 JSON 형식을 먼저 합의하고 구간별로 따로 만들어 이음, 이슈 → PR → 자동 검사 2개(리뷰, 공개 범위 검사), 주 3회 회의와 회의록, 공개 저장소 자동 게시.

## 3. 더 강조할 포인트

지금은 문서나 관리자 화면에 묻혀 있어 발표에서 따로 꺼내야 하는 강점입니다.

1. **"교육과정이 덮지 못하는 기술" 지표.**
   채용 수요는 있는데 AWS 과정이 없거나 관련 과정만 있는 기술을 보여 줍니다(관리자 화면 "과정 커버리지" 탭, 시장 Gap = 수요 비중 − 공급 비중).
   학습자에게는 "이 기술은 AWS 과정으로 못 채운다"는 정직한 안내이고, **교육과정을 만드는 쪽에는 어떤 과정이 비어 있는지 알려 주는 자료**입니다. 주제 제공사가 바로 그 당사자입니다.
   현장 적용성과 창의성을 함께 받을 수 있는 유일한 포인트라 장표 한 장을 따로 줍니다.
2. **LLM을 그대로 믿지 않는 구조.**
   근거 문장은 코드가 원문과 대조하고, 숫자는 코드가 세고, 추천 이유는 별도 호출이 검토한 뒤 코드가 한 번 더 검사합니다.
   "그럴듯한 답"이 아니라 "검증을 통과한 답만 화면에 나온다"는 문장으로 말합니다. 주제 설명의 "근거 없는 분석이면 부족"에 정면으로 답합니다.
3. **데이터로 고르는 운영.**
   모델 비교와 추천 구조 A/B 실험이 있고, 좋아요 비율과 턴당 비용으로 모델을 고르는 규칙이 코드에 있으며 결정 기록이 남습니다(`backend/experiments.py`).
   실패한 시도도 씁니다: 팀장 구조는 실제 실행에서 과정 카드를 내지 못해 채택을 보류했고, Bedrock Agents는 계정에서 만들 수 없어 Converse 도구 호출로 직접 구현했습니다. "측정해서 정했다"가 메시지입니다.
4. **모르는 것을 모른다고 하는 설계.**
   PyTorch가 수요에 없는 것은 약점이지만, 관리자 화면의 "사전에 없어 세지 못한 기술 상위 20개"와 묶으면 운영자가 사전을 넓히는 점검 고리가 됩니다.
   질문을 기다리지 말고 한계 장표에서 먼저 말합니다.
5. **개인정보와 안전.**
   저장 전에 이메일·전화번호·주민등록번호 모양을 코드로 가리고, 대화는 30일 뒤 지우며, 비회원 대화와 차단된 발화는 저장하지 않습니다. 실험 기록에는 발화 내용이 없습니다.
   가드레일은 정상 문장이 잘못 막히던 오탐("지방에 살아서 오프라인 수업은 안 맞아요" 등)을 리뷰에서 찾아 고친 사례가 있습니다. 현재 설정은 보지 않은 10문항에서 오탐 0/5, 미탐 0/5입니다(11/19, 1회. 통과해야 할 문항이 5개뿐이라는 한계를 같이 말합니다).
6. **스스로 한계를 적은 평가.**
   개선용 점수를 문서에서 "과대평가"라고 적어 두었습니다. 질의응답에서 신뢰를 주는 태도입니다. 다만 채점용 수치가 없으면 "그래서 실제 점수는?"에 답할 수 없어 역효과가 납니다(4절 1번).

## 4. 감점 위험과 발표 전 대응

코드 변경 없이 할 수 있는 것만 적었습니다. 위에서부터 급한 순서입니다.

| 위험 | 대응 | 담당 |
| --- | --- | --- |
| 추출 정확도를 물으면 가짜 공고 10건의 점수(F1 0.977)뿐 | 채점용 50건 최종 평가를 돌려 그 수치를 넣는다. 못 돌리면 0.977은 "개선용 점수"라고 밝히고 쓴다 | 성진 |
| 사용자 테스트 수치 없음 | 진행 중인 설문 결과를 채운다. 참여자 수와 문항별 응답만 있어도 된다 | 형섭 |
| "Lambda는 어디에 쓰나" | 실제 배포 구성을 확인한다. 쓰지 않았다면 이유로 답한다: 공고마다 따로 실행하면 직무별 배치 하나라는 전제가 깨지고 집계 시점을 정할 수 없다(`docs/dynamodb-design.md` 6절) | 일현 |
| 문서와 그림에 "Bedrock Agents", "기술 추출 Lambda"가 남아 코드와 다름 | 발표 장표는 코드 기준으로 새로 그린다. `docs/service-flow.md`는 공개 범위라 함께 고칠지 정한다 | 일현 |
| AI 직무에 PyTorch 등이 없고, 상위 기술에 과정이 없으면 추천 카드가 빌 수 있음 | 시연은 클라우드 엔지니어로 한다. AI는 건수와 3절 4번으로 설명한다 | 성진 |
| 기준 단계가 전부 추정 3단계 "(불확실)"로 나옴(저장소의 `data/required_levels.json`이 비어 있음) | 배포 환경에서 확인하고, 그대로면 시연에서 "기준은 팀 추정값"이라고 먼저 말한다 | 종훈 |
| 사람 리뷰가 없다는 지적 | 자동 검사 2개와 회의에서의 검토로 설명하고, 팀원별 PR 분포를 보여 준다 | 형섭 |
| 유사 서비스 비교표 없음 | 표를 만들거나, 3절 1·2번을 차별점으로 대신한다 | 형섭 |
| 페르소나 통계의 원 보고서 미확인 | 확인한 수치만 첫 장에 쓴다 | 형섭 |
