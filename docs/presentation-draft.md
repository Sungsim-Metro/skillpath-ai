# 발표 초안

2026-11-21 작성. 11/25 발표(15분 + 질의응답 7분)의 초안입니다. 시간 배분은 아직 넣지 않았고, **과제 안내 자료의 요구를 충족했는지**와 **평가 기준별로 점수를 받을 포인트**를 먼저 정리했습니다.
시연 순서는 [시연 시나리오](demo-scenario.md)에 있습니다.

기준으로 삼은 것:

- 과제 안내 자료(AWS 주제 설명 6쪽): 5단계 흐름, 최종 화면의 목표, 역할 분리 원칙, 세 질문.
- 가장 최근에 안내된 평가 기준: "기술 완성도, 분석 품질, 추천 성능, 발표 및 시연, 팀워크 등을 기준으로 종합 평가합니다. 특정 데이터 소스의 사용 여부에 따른 별도 가점이나 감점은 없습니다."

숫자는 저장소 문서에 있는 값만 썼습니다. 값이 없는 곳은 지어내지 않고 **[채울 칸]** 으로 두었습니다(7절).

## 1. 과제 안내 자료 대비 충족 진단

### 5단계 흐름

## 2. 평가 기준별 득점 포인트

### 기술 완성도

- **끝까지 연결되어 실제로 동작한다.** 수집 → 추출 → 표준화 → 분석 → 추천이 한 흐름이고, 배포 주소에서 라이브로 보여 줍니다.
- **안내 자료의 역할 분리 원칙을 구조로 만들었다.** LLM은 읽고 설명하고, 숫자는 코드가 세고, LLM의 출력은 코드 검사를 통과해야 화면에 나옵니다.
- **AWS 서비스마다 고른 이유가 있다.** 코드에서 확인되는 것만 그립니다(5절 장표 5의 표).
- **운영을 고려했다.** 호출마다 토큰 기록, 관리자 화면의 비용 집계, 입력 가드레일, 개인정보 가림과 30일 삭제, 모의 모드.
- 응답 46.2초 → 9.8초, 추천 화면의 모델 호출 6번 → 3번(다시 그리면 0번).

### 분석 품질

- **근거.** 추출한 기술마다 공고 원문 문장이 있고, 그 문장이 본문에 실제로 있는지 코드가 확인합니다. 개선용 데이터에서 지어낸 근거 0건.
- **표준화.** 안내 자료의 예시(아마존 웹 서비스 = AWS, Java ≠ JavaScript)를 테스트로 지킵니다. 임베딩이 JavaScript의 1순위 후보로 Java를 내도 합치지 않습니다.
- **불확실을 세지 않는다.** 불확실 비율 56.2% → 11.6%(실제 공고 12건, 1회). 남은 불확실은 수요에 넣지 않습니다.
- **두 가지 분석.** 개인 Gap(내 단계와 기준 단계)과 시장 Gap(수요 비중 − 공급 비중). NCS 능력단위와 연결.
- **데이터의 한계를 숫자로 적었다.** AWS 수요율 74%는 선정 조건 때문에 실제보다 높다고 밝힙니다.
- 채점용 50건 평가 수치 **[채울 칸]**. 이 기준에서 가장 필요한 숫자입니다.

### 추천 성능

- **추천 이유를 검증한다.** 공고 수요 수치와 그 과정의 학습 목표 원문으로 이유를 쓰고, 별도 호출이 검토한 뒤 코드가 최종 검사합니다. 통과한 과정만 표시합니다.
- **안내 자료가 요구한 네 가지를 카드에 담았다.** 이유, 링크, 난이도, 선수지식. 여기에 평점과 학습 순서를 더했습니다.
- **맞지 않는 추천을 줄였다.** Kubernetes와 Docker가 함께 받던 과정 3개(모두 확신) → 1개(불확실).
- **"과정 없음"도 결과다.** AWS 서비스가 아닌 기술은 "유사 과정"으로, Python은 과정 없음으로 둡니다.
- **추천 방식을 실험으로 비교한다.** 추천 구조 A/B, 모델 비교, 비용 규칙.
- 추천 품질 점수(과정 검색 정답 52개 기술 기준)와 사용자 테스트의 "추천이 적절했나" 응답 **[채울 칸]**.

### 발표 및 시연

- 라이브 시연이 세 질문에 화면으로 답합니다. 단계마다 "지금 보신 것이 질문 몇 번의 답"이라고 말합니다.
- 안내 자료의 용어와 순서를 그대로 씁니다(5단계 이름, "무엇이 · 왜 · 무엇을 공부"). 심사위원이 자기 기준표와 바로 맞춰 볼 수 있습니다.
- 장표마다 숫자 하나와 한 문장.
- 마지막 장은 세 질문의 답을 한 줄씩 다시 보여 줍니다.

### 팀워크

- 안내 자료의 네 역할과 우리 분담이 그대로 대응합니다.
- `contracts/`의 JSON 형식을 먼저 합의하고 구간별로 따로 만들어 이었습니다.
- 이슈 → PR → 자동 검사 2개(리뷰, 공개 범위 검사), 주 3회 회의와 회의록, 공개 저장소 자동 게시.
- 개선 기록에 누구의 작업 덕분인지 표시되어 있어, 한 개선에 여러 사람이 이어 기여한 사례를 보여 줄 수 있습니다(예: 불확실 비율 개선은 종훈의 사전과 성진의 프롬프트).

## 3. 더 강조할 포인트

지금은 문서나 관리자 화면에 묻혀 있어 발표에서 따로 꺼내야 하는 강점입니다.

1. **안내 자료의 예시를 그대로 통과한다.**
   안내 자료 3쪽의 가상 공고("Python을 활용한 개발 경험과 AWS 환경 운영 경험 필수, Docker 사용 경험 우대.")와 표준화 예시 두 개는 심사위원이 가장 잘 아는 입력입니다.
   이 문장을 우리 서비스에 넣은 결과를 장표나 시연에 보여 주면 "요구한 것을 만들었다"가 한 번에 전달됩니다. 결과는 미리 돌려 확인한 뒤 씁니다 **[채울 칸]**.
2. **"교육과정이 덮지 못하는 기술" 지표.**
   채용 수요는 있는데 AWS 과정이 없거나 관련 과정만 있는 기술을 보여 줍니다(관리자 화면 "과정 커버리지").
   안내 자료는 목표 사용자로 "취업 준비생? 교육과정 설계자?"를 물었습니다. 우리는 취업 준비생을 골랐지만 이 지표는 **교육과정 설계자에게도 답**이 됩니다. 분석 품질과 추천 성능 양쪽에 걸립니다.
3. **LLM을 그대로 믿지 않는 구조.**
   근거 문장은 코드가 원문과 대조하고, 숫자는 코드가 세고, 추천 이유는 별도 호출과 코드 검사를 통과해야 화면에 나옵니다.
   안내 자료의 "유사 문서를 찾았다 ≠ 정확한 매칭"을 가장 멀리 밀고 간 부분입니다.
4. **시장 분석과 개인 진단을 둘 다 만들었다.**
   안내 자료는 둘을 구분하라고 했습니다. 우리는 5단계 수준 진단과 대화로 개인 역량을 받고, 학습 순서까지 코드로 정합니다.
5. **데이터로 고르는 운영.**
   모델·추천 구조 비교 실험, 좋아요 비율과 턴당 비용으로 모델을 고르는 코드 규칙, 결정 기록(`backend/experiments.py`).
   실패한 시도도 씁니다: 팀장 구조는 실제 실행에서 과정 카드를 내지 못해 채택을 보류했습니다.
6. **모르는 것을 먼저 말한다.**
   PyTorch가 수요에 없는 것은 약점이지만, 관리자 화면의 "사전에 없어 세지 못한 기술 상위 20개"와 묶으면 운영자가 사전을 넓히는 점검 고리가 됩니다. 한계 장표에서 먼저 꺼냅니다.
7. **개인정보와 안전.**
   저장 전에 이메일·전화번호·주민등록번호 모양을 코드로 가리고, 대화는 30일 뒤 지우며, 비회원 대화와 차단된 발화는 저장하지 않습니다.
   가드레일은 정상 문장이 잘못 막히던 오탐("지방에 살아서 오프라인 수업은 안 맞아요" 등)을 리뷰에서 찾아 고쳤습니다. 현재 설정은 보지 않은 10문항에서 오탐 0/5, 미탐 0/5입니다(11/19, 1회. 통과해야 할 문항이 5개뿐이라는 한계를 같이 말합니다).

## 4. 감점 위험과 발표 전 대응

코드 변경 없이 할 수 있는 것만 적었습니다. 위에서부터 급한 순서입니다.

| 위험 | 걸리는 기준 | 대응 | 담당 |
| --- | --- | --- | --- |
| 추출 정확도를 물으면 가짜 공고 10건의 점수(F1 0.977)뿐 | 분석 품질 | 채점용 50건 최종 평가를 돌려 그 수치를 넣는다. 못 돌리면 0.977은 "개선용 점수"라고 밝히고 쓴다 | 성진 |
| 추천 품질 점수 없음 | 추천 성능 | 과정 검색 정답(52개 기술)으로 평가를 한 번 돌리거나, 사용자 테스트의 "추천이 적절했나" 응답을 쓴다 | 성진, 형섭 |
| 필수/우대 구분이 안내 자료의 2단계 요구인데 데이터 한계로 약함 | 분석 품질 | 화면 값이 어떻게 나오는지 확인한다. 구분하지 못한 공고가 많으면 이유(구역 제목이 지워진 데이터)를 먼저 말한다 | 종훈 |
| 산업별 분석이 4단계 요구인데 대부분의 공고에 산업 값이 없음 | 분석 품질 | 직무별 분석으로 설명하고, 산업 값이 없는 이유를 한계에 적는다 | 종훈 |
| "Lambda는 어디에 쓰나"(안내 자료가 두 번 언급) | 기술 완성도 | 실제 배포 구성을 확인한다. 쓰지 않았다면 이유로 답한다: 공고마다 따로 실행하면 직무별 배치 하나라는 전제가 깨지고 집계 시점을 정할 수 없다(`docs/dynamodb-design.md` 6절) | 일현 |
| 문서와 그림에 "Bedrock Agents", "기술 추출 Lambda"가 남아 코드와 다름 | 기술 완성도 | 발표 장표는 코드 기준으로 새로 그린다. `docs/service-flow.md`는 공개 범위라 함께 고칠지 정한다 | 일현 |
| AI 직무에 PyTorch 등이 없고 추천 카드가 빌 수 있음 | 분석 품질, 추천 성능 | 시연은 클라우드 엔지니어로 한다. AI는 건수와 3절 6번으로 설명한다 | 성진 |
| 기준 단계가 전부 추정 3단계 "(불확실)"로 나옴(저장소의 `data/required_levels.json`이 비어 있음) | 분석 품질 | 배포 환경에서 확인하고, 그대로면 시연에서 "기준은 팀 추정값"이라고 먼저 말한다 | 종훈 |
| 사용자 테스트 수치 없음 | 추천 성능, 발표 | 진행 중인 설문 결과를 채운다 | 형섭 |
| 사람 리뷰가 없다는 지적 | 팀워크 | 자동 검사 2개와 회의에서의 검토로 설명하고, 팀원별 PR 분포를 보여 준다 | 형섭 |

## 5. 장표 구성

안내 자료의 순서와 용어를 따르고, 평가 기준 다섯 개가 장표 묶음과 하나씩 대응하게 했습니다. 시간은 내용이 정해진 뒤에 맞춥니다.

| # | 묶음 | 장표 | 핵심 문장 | 넣을 것 |
| --- | --- | --- | --- | --- |
| 1 | 도입 | 문제와 목표 사용자 | 채용공고를 읽고도 무엇을 공부할지 알 수 없다 | 목표 사용자 한 명, 확인된 통계 1~2개 |
| 2 | 도입 | 만든 것 | 공고 → 기술 → 표준화 → 분석 → 교육 추천을 끝까지 이었다 | 안내 자료의 5단계 그림에 우리 구현을 얹은 한 장. "무엇이 · 왜 · 무엇을 공부" |
| 3 | 발표 및 시연 | 라이브 시연 | 경험 한 문장에서 추천 과정까지 | [시연 시나리오](demo-scenario.md) |
| 4 | 기술 완성도 | 공고 1건에서 917건까지 | 작은 입력 하나를 끝까지 처리한 뒤 넓혔다 | 안내 자료의 가상 공고를 넣은 결과 **[채울 칸]**, 확장 과정 |
| 5 | 기술 완성도 | AI가 할 일과 코드가 할 일, AWS 구성 | 읽고 설명하는 일은 AI, 세고 검사하는 일은 코드 | 역할 분리 표, 아래 서비스 표 |
| 6 | 분석 품질 | 질문 1: 어떤 데이터를 분석했나 | 실제 채용공고 917건(클라우드 230, AI 687)을 두 출처에서 모았다 | 출처, 기간, 거른 과정, 한계 3개 |
| 7 | 분석 품질 | 질문 2: 어떤 근거로 필요하다고 판단했나 | 기술마다 공고 원문 문장이 있고, 코드가 그 문장을 확인한다 | 근거 문장 화면, 표준화 예시(아마존 웹 서비스 = AWS, Java ≠ JavaScript), 불확실은 세지 않음, 채점 수치 **[채울 칸]** |
| 8 | 분석 품질 | 시장 분석과 개인 진단 | 시장이 요구하는 것과 내가 부족한 것을 따로 본다 | 직무별 수요, NCS 연결, 5단계 수준 진단, 레이더 |
| 9 | 추천 성능 | 질문 3: 왜 이 과정을 추천했나 | 이유, 링크, 난이도, 선수지식. 검토를 통과한 과정만 | 추천 카드, 검증 3단계(작성 → 검토 → 코드 검사), "유사 과정" |
| 10 | 추천 성능 | 교육과정이 덮지 못하는 기술 | 수요는 있는데 과정이 없는 기술을 찾았다 | 과정 커버리지 숫자 **[채울 칸: 배포 환경 값]**, 대표 기술 |
| 11 | 추천 성능 | 측정하고 고쳤다 | 숫자로 문제를 찾고 숫자로 확인했다 | 개선 전후 3~4개, 추천 구조·모델 비교, 사용자 테스트 **[채울 칸]** |
| 12 | 팀워크 | 역할과 협업 | 형식을 먼저 합의하고 구간별로 만들어 이었다 | 역할 4명, 계약, PR 흐름, 여러 사람이 이어 만든 개선 사례 |
| 13 | 마무리 | 한계와 다음 | 모르는 것은 먼저 말한다 | 신입 전용 수요, 필수/우대와 산업 값, AI 기술 사전, AI 기준 단계 |
| 14 | 마무리 | 세 질문의 답 | 근거 있는 학습경로를 만드는 AI | 질문 세 개와 한 줄 답, 소개 페이지 주소와 QR |

장표 5에 넣을 서비스(코드에서 확인한 것):

| 서비스 | 어디에 | 왜 |
| --- | --- | --- |
| Amazon Bedrock (Claude, Converse) | 공고 추출, 상담 발화 해석, 추천 이유 작성·검토 | 표현이 일정하지 않은 문장을 읽고 설명하는 일 |
| Bedrock Guardrails | 상담 입력 검사 | 주제 밖 질문과 차별 조건을 모델 호출 전에 차단 |
| Bedrock Knowledge Base + S3 Vectors | 교육과정 검색 | 부족 기술에 맞는 과정을 의미로 검색. 저장·질의한 만큼만 과금 |
| Titan Embeddings | 표현 표준화, 과정 벡터 | 같은 뜻의 다른 표현 묶기 |
| S3 | 수집한 공고 JSON, 과정 문서 | 근거 검증과 재실행에 같은 데이터 사용 |
| DynamoDB | 추출 결과, 수요 집계, 프로필, 대화 기록, 실험 기록 | 직무별 집계를 화면이 바로 읽음. 대화는 TTL로 삭제 |
| CloudFormation | Knowledge Base 구성 | 같은 구성을 다시 만들 수 있음 |
| Streamlit | 사용자 화면 | 안내 자료가 제시한 화면 도구 |

Lambda, CloudWatch, 앱 서버(배포 주소)는 실제 구성을 확인한 뒤 넣습니다 **[채울 칸]**.

## 6. 예상 질문과 답

답은 "결론 → 근거 하나 → 다음 행동" 순서로 짧게 하고, 그 구간을 만든 사람이 답합니다.

| 질문 | 답의 방향 | 답할 사람 |
| --- | --- | --- |
| 추출 정확도는 | 채점용 50건 수치 **[채울 칸]**. 근거 문장은 코드로 대조해 지어낸 근거를 걸러 낸다 | 성진 |
| 추천이 적절한지 어떻게 아나 | 학습 목표 원문으로 이유를 검증하고 통과한 과정만 보여 준다. 수치 **[채울 칸]** | 성진 |
| 필수와 우대는 어떻게 구분했나 | 확인 결과에 따라 답 **[채울 칸]**. 구역 제목이 없는 공고는 나누지 않았다 | 종훈 |
| 산업별 분석은 | 직무별로 분석했다. 대부분의 공고에 산업 값이 없어 산업별은 하지 않았다 | 종훈 |
| AI 엔지니어 분석에 PyTorch가 왜 없나 | 표준 기술 사전에 없어 "불확실"로 남겼고 그럴듯하게 채우지 않았다. 세지 못한 기술 목록을 관리자 화면에서 보고 사전을 넓힌다 | 성진 |
| Lambda와 Bedrock Agents를 왜 안 썼나 | Lambda는 4절의 답. Agents는 계정에서 만들 수 없어 Converse 도구 호출로 같은 역할을 구현했다 | 일현, 성진 |
| 경력 공고로 신입에게 추천해도 되나 | 필요한 역량 자체는 같다. 이 서비스는 추천이지 실력 검증이 아니다. 신입 전용 수요를 못 보는 것은 한계로 적었다 | 형섭 |
| 고용24를 쓰지 않은 이유, 약관 문제 | 데이터 소스에 따른 가점·감점은 없다고 안내받았다. AWS 과정은 대회 측 확인을 받았고, 원티드는 약관 확인 뒤 조회를 중단했다 | 종훈 |
| 운영 비용은 | 월 운영비 추정 **[채울 칸]**. 호출 수를 6번에서 3번으로 줄였고 턴당 비용으로 모델을 고른다 | 일현 |
