# 추천 이유 채점 (LLM 채점과 사람 재채점)

2026-11-16 결정. 개발 중에 돌리는 평가이고 서비스가 돌 때는 부르지 않습니다. 스크립트는 `ai/eval/judge.py`, 프롬프트는 `ai/prompts/judge_v1.py`.

## 무엇을 재나

추천 이유(③ `courses[].reason`)에는 정답이 하나로 정해져 있지 않아 정답지와 비교할 수 없습니다.
그래서 기준표를 정하고 LLM이 항목마다 점수를 매기게 한 뒤, 일부를 사람이 같은 기준표로 다시 매겨 둘이 얼마나 같은지 봅니다.
일치율이 낮으면 LLM 채점 결과를 쓰지 않습니다.

채점 항목 하나는 (부족 기술, 과정, 추천 이유)입니다.

## 채점 기준표

| 기준 | 2점 | 1점 | 0점 |
| --- | --- | --- | --- |
| 근거 충실 (`grounded`) | 이유가 말한 과정 내용이 모두 그 과정의 학습 목표나 제목에 있다 | 대체로 있지만 학습 목표에서 확인되지 않는 내용이 하나 있다 | 학습 목표에 없는 내용을 주로 말하거나, 과정 내용을 말하지 않는다 |
| 검색 관련성 (`relevant`) | 과정의 제목이나 학습 목표가 부족 기술을 직접 다룬다 | 직접 다루지는 않지만 그 기술을 배우는 데 필요한 관련 기초를 다룬다 | 부족 기술과 관련이 약하거나 없다 |
| 이해하기 쉬움 (`clear`) | 취업 준비생이 읽고 왜 이 과정을 들어야 하는지 바로 알 수 있다 | 뜻은 통하지만 모호하거나 번역투여서 다시 읽어야 한다 | 무슨 말인지 알기 어렵거나 이 과정을 들어야 할 이유가 없다 |

`relevant`는 추천 이유가 아니라 **과정을 고른 검색**의 품질을 잽니다. 단일 추천과 토론 추천은 같은 과정을 받으므로 이 기준으로 둘을 비교하지 않습니다.
이유의 품질은 `grounded`와 `clear`로 봅니다.

공고 수 같은 숫자가 맞는지는 채점하지 않습니다. 숫자는 코드(`ai/recommend.py`의 `validate_reasons`)가 검사합니다.
이 표를 고치면 `ai/prompts/judge_v1.py`의 `RUBRIC`도 같이 고칩니다. 한쪽만 고치면 일치율이 뜻을 잃습니다(`ai/test_judge.py`가 두 곳이 글자까지 같은지 검사합니다).

## 순서

```bash
# 1. 추천을 만들고 LLM 이 채점한다. 단일 추천과 토론 추천을 같은 입력으로 비교한다
python -m ai.eval.judge run

# 2. outputs/eval/judge_..._human.csv 를 열어 grounded, relevant, clear 칸에 0·1·2 를 적는다 (사람)

# 3. 일치율을 계산한다
python -m ai.eval.judge agree outputs/eval/judge_bedrock_....json outputs/eval/judge_bedrock_..._human.csv --rater 이름

# 지금 가진 평가 케이스 수(추출 정답의 기술 항목, 채점 항목. 종류가 달라 합치지 않는다)
python -m ai.eval.judge cases
```

- 실제 모드는 `BEDROCK_MOCK=0`과 `BEDROCK_MODEL_ID`가 필요합니다. 호출 수는 (기술 수 × 비교 수)번의 채점에 추천 호출이 더해집니다.
- `JUDGE_MODEL_ID`를 주면 채점만 그 모델로 합니다. 추천을 쓴 모델이 자기 글을 채점하면 후하게 줄 수 있어, 다른 모델을 쓸 수 있으면 씁니다.
- 가짜 모드(`BEDROCK_MOCK=1`)의 점수는 형식 확인용 예시입니다. 발표와 보고서에 쓰지 않습니다.

## 사람이 다시 보는 항목

- 글자까지 같은 (기술, 과정, 이유)는 한 번만 넣습니다. 지금 데이터로는 20개 안팎이라 기본값은 **전부**입니다.
- `--human N`으로 줄여도 LLM이 2점 미만을 준 항목, 검증에서 걸린 항목(수정됨, 불확실, 반박 기각), "불확실" 과정은 전부 들어갑니다.
  무작위로만 뽑으면 전부 2점인 항목만 걸려 일치율이 저절로 높게 나옵니다.
- 엑셀로 열었으면 "CSV UTF-8(쉼표로 분리)"로 저장합니다. 한국어 엑셀의 기본 CSV도 읽습니다. 같은 `item_id`가 두 번 나오면 오류입니다.

## 사람 재채점 규칙

- 양식에는 LLM 점수와 "단일/토론" 구분이 없습니다. 보고 따라 매기지 않게 하려는 것입니다. 결과 JSON을 먼저 열어 보지 않습니다.
- 과정 페이지를 따로 열지 않고 양식에 있는 학습 목표만 보고 매깁니다. LLM 채점자와 같은 정보로 매겨야 비교가 됩니다.
- 애매하면 낮은 점수를 주고 `memo` 칸에 이유를 적습니다.
- 채점자는 추천 프롬프트를 고친 사람이 아닌 편이 좋습니다. 같은 사람이면 그렇게 적습니다.

## 결과를 읽는 법

- `run`의 표: 비교 대상마다 기준별 평균(0~2)과 합계 평균(0~6), "불확실"로 남은 과정 수, 그리고 기준별 점수 분포.
  한 기준의 점수가 전부 같으면 그 기준은 항목을 가려내지 못한 것이라 경고가 나옵니다.
- 단일과 토론 둘 다 돌렸으면 같은 과정의 쌍을 둘로 나눠 셉니다.
  - **이유나 판정이 바뀐 쌍**: 토론의 효과는 여기서만 읽습니다. 높아진·같은·낮아진 쌍의 수.
  - **이유가 글자까지 같은 쌍**: 같은 글을 두 번 채점한 것입니다. 여기서 점수가 달라진 쌍의 수가 채점 잡음입니다. 바뀐 쌍의 차이가 이 수보다 작으면 효과라고 말하지 않습니다.
- `agree`의 표: 기준마다 정확히 같은 항목 수, 평균 차이(LLM − 사람, +면 LLM이 후함), 교차표(사람 점수 × LLM 점수),
  그리고 **사람이 2점 미만을 준 항목 가운데 LLM도 2점 미만을 준 수**. 마지막 숫자가 "LLM 채점이 나쁜 이유를 잡아내는가"의 답입니다.
  "1점 이내 일치"는 내지 않습니다. 점수가 셋뿐이라 거의 언제나 100%에 가깝습니다.
- 채점한 사람과 결과는 `..._agreement.json`으로 저장됩니다. 발표에는 이 파일의 숫자를 씁니다.
- 결과 JSON에는 실행 시각, 모델, 프롬프트 버전, 항목 수, 토큰 수가 남습니다. 발표에 숫자를 쓸 때 이 값을 함께 적습니다.

## 한계

- 수요 숫자는 가짜 `data/sample/demand.json`에서 옵니다(`recommend_demo.py`와 같음). 결과 JSON의 `demand_source`에 남습니다. 실제 수요 집계가 연결되면 바꿉니다.
- 추천할 과정이 없는 기술(지금은 Python, Network, Java, Azure, Go)은 채점 항목이 없습니다. "과정이 없다"는 문제는 이 평가에 잡히지 않습니다.
- 항목 수가 적습니다(기술 수 × 과정 최대 3개). 평균의 작은 차이를 "개선"이라고 말하지 않습니다. 높아진·낮아진 쌍의 수를 함께 봅니다.
- 토론 추천이 단일 추천보다 낫지 않게 나올 수 있습니다. 그 결과도 그대로 적습니다.
- 상담 답변 채점은 상담 Agent(#25)가 만들어진 뒤에 같은 방식으로 더합니다. 지금은 추천 이유만 채점합니다.
- 추출 정답지는 이 스크립트가 만들지 않습니다. 기존 절차(`GOLD_RULES.md`, `make_gold_template.py`)대로 사람이 씁니다.
